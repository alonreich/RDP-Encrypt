SECTION 0 — TL;DR (READ THIS FIRST)
--------------------------------------------------------------------------------
RDP Vault is a multi-platform security vault for Windows and Android.
It stores RDP connection profiles (hosts, ports, usernames, optional passwords)
inside ONE encrypted file ("vault.rdpv"). 

On Windows:
It is a self-contained single-file Avalonia UI application. It launches connections
through Windows' own mstsc.exe and removes the local traces that mstsc leaves behind
(registry history, Default.rdp, jump lists, recent items, and — when the user
opts in — UserAssist, prefetch and saved TERMSRV credentials). It supports
automatic re-locking, an optional (off by default) self-destruct, a printed
Recovery Code, Windows Hello quick unlock backed by the machine TPM, and
one-click desktop shortcuts.

On Android:
It is a mobile companion application (RDPVault.Android) sharing the identical
cryptographic core (RDPVault.Core) and vault.rdpv file format. It seals master
keys inside the device's hardware Secure Element / ARM TrustZone TEE via Android
Keystore and StrongBox Keymaster, gated by Class 3 Strong Biometrics (fingerprint/3D face).
It provides zero-compromise session continuity across orientation flips via a
bound ForegroundService (RdpSessionService), standard RDP intent handoff (rdp://),
automatic certificate warning suppression, and zero-clipboard credential isolation
(passwords never touch the Android system clipboard or IME caches).

If you are an AI agent asked to modify this project: read SECTIONS 4, 5, 6, 10,
13, and 18 before touching anything. Do not weaken the crypto. Do not write any
secret to disk outside vault.rdpv. Do not reintroduce anything from the
"REGRESSIONS TO NEVER REINTRODUCE" list in SECTION 13.

SECTION 1 — WHO USES THIS AND WHY (PRODUCT CONTEXT)
--------------------------------------------------------------------------------
Target user : A person who connects via RDP to their own or company computers
              and wants:
              (a) no residue on the host PC they launch from — so a later user
                  of that PC cannot see which host was contacted;
              (b) one click to connect to a stored host:port, with credentials
                  optionally saved;
              (c) automatic re-lock after inactivity, WITHOUT killing running
                  RDP sessions;
              (d) on trusted PCs, unlock with Windows Hello instead of typing
                  the master password;
              (e) desktop shortcuts for frictionless connections;
              (f) a way back in if they forget the master password.

Usage model : Portable (run the exe from a USB stick next to its vault.rdpv) or
              installed to %LOCALAPPDATA%\RDPVault via the built-in installer.
              Single instance is enforced per Windows session via a named mutex
              plus a NamedPipe that forwards --launch requests.

SECTION 2 — TECHNOLOGY STACK (EXACT)
--------------------------------------------------------------------------------
Language        : C# 12, nullable reference types ENABLED, implicit usings ON.

WINDOWS DESKTOP STACK:
Platform        : .NET 9, TFM net9.0-windows10.0.19041.0 (WinRT projections for
                  the Windows Hello APIs).
UI framework    : Avalonia UI 11.1.3 (XAML + code-behind; the shared dialogs are
                  built in code — see Dialogs.cs).
Output type     : WinExe, published SELF-CONTAINED SINGLE FILE (compiled\RDPVault.exe).

  *** PACKAGING & PERFORMANCE CHARACTERISTICS: ***
  1. PublishSingleFile=true, SelfContained=true, PublishReadyToRun=false.
  2. EnableCompressionInSingleFile=false: Disabling single-file bundle compression
     trades disk footprint (~56MB compressed vs ~115MB uncompressed) for instant
     startup. With compression enabled, every double-click caused a 7-10s delay while
     the CPU decompressed 115MB+ of assemblies into memory. Storing uncompressed allows
     Windows to memory-map the binary directly, cutting cold start down to <600ms.
  3. IncludeNativeLibrariesForSelfExtract=true: Required by Avalonia/SkiaSharp so native
     binaries (libSkiaSharp.dll) are extracted into %TEMP%\.net\RDPVault and load cleanly,
     preventing DllNotFoundException on startup.
  4. app.manifest: Configured with <requestedExecutionLevel level="asInvoker" uiAccess="false" />.
     Eliminates artificial UAC delays on launch; elevation is performed on-demand
     programmatically with RunAs when installing or uninstalling.
  5. PublishAot=false and PublishTrimmed=false: ShellLink.cs uses COM interfaces (IShellLinkW,
     IPersistFile) and WinRT projections plus managed Argon2 are not compatible with full AOT/trimming.

SECTION 4 — CRYPTOGRAPHY SPEC (EXACT PARAMETERS — DO NOT WEAKEN)
--------------------------------------------------------------------------------
KDF (password -> key):
  Argon2id (Isopoh Argon2Type.HybridAddressing == Argon2id;
  Argon2Version.Nineteen == v1.3).
  Salt      : 32 random bytes, base64 in the vault file. RE-SALTED on every
              password change.
  Memory    : 65536 KiB (64 MiB).   Iterations: 3.   Lanes/Threads: 4.
  Output    : 32 bytes, zeroed after use. The UTF-8 copy of the secret is also
              zeroed and the Argon2 instance disposed (v1.0.0 did neither).

  NOTE: v1.0.0's Models.cs actually defaulted to 262144 KiB / t=5 while this
  document claimed 64 MiB / t=3. 1.1.0 makes the code match the spec. Existing
  vaults carry their own Kdf block and keep using it, so old 256 MiB vaults
  still open — they simply stay slow until the password is changed.

Cipher: AES-256-GCM, 12-byte random nonce per seal, 16-byte tag appended.

Key hierarchy:
  masterPassword --Argon2id(Kdf)--> passwordKey --AES-GCM--> Wrap     (masterKey)
  RecoveryCode   --Argon2id(RecoverySalt)--> recoveryKey --AES-GCM--> Recovery
  TPM signature  --Argon2id(Kdf.Salt)--> tpmKey --AES-GCM--> Seals[i].TpmBlob
  payload JSON   --AES-GCM(masterKey)--> Data

RECOVERY CODE (new in 1.1.0 — the v1.0.0 "24-word paper key" did not exist):
  256 bits of entropy rendered as 52 Crockford-Base32 characters in 13 groups of
  4 (alphabet 0-9 A-Z minus I, L, O, U). Input is normalised — case, dashes and
  spaces ignored, I/l -> 1, O -> 0, U -> V — then fed to Argon2id as the secret.
  The code is displayed exactly once, at creation or when regenerated, and is
  NOT recoverable from the vault. It wraps the same masterKey, so it survives
  password changes.

Quick-unlock hardware binding (per PC):
  MachineId = first 8 bytes of SHA-256("{MachineName}|{UserDomain}|{UserName}").
  Hello proof = KeyCredential.RequestSignAsync over
      "RDPVault::QuickUnlock::v2::<MachineId>".
  The raw TPM signature feeds Argon2id to derive tpmKey. That only works if the
  signature is byte-reproducible, so enrollment signs TWICE and compares, and
  test-unseals the new seal before saving it. If the signature is randomised
  (PSS / ECDSA), enrollment refuses and says so instead of silently creating a
  seal that can never open.

Vault file format (vault.rdpv = UTF-8 JSON, minified). V=2:
{
  "V": 2,
  "Kdf":   { "Salt": "<b64>", "Mem": 65536, "Iter": 3, "Lanes": 4 },
  "Wrap":  { "Nonce": "<b64>", "Ct": "<b64 ct||tag>" },
  "Recovery": { "Nonce": "<b64>", "Ct": "<b64>" },   // absent in V1 vaults
  "RecoverySalt": "<b64>",
  "Seals": [ { "MachineId": "<16 hex>", "TpmBlob": "<nonce>:<ct>", "KeyId": "<64 hex>" } ],
  "Policy": { "SelfDestructEnabled": false, "MaxAttempts": 25,
              "WindowMinutes": 60, "ThrottleEnabled": true },
  "Fails":  { "Count": 0, "FirstFailUtc": "...", "LastFailUtc": "..." },
  "Data":  { "Nonce": "<b64>", "Ct": "<b64>" }
}
Policy and Fails are DELIBERATELY unencrypted: they must be readable while the
vault is locked, they contain no secrets, and keeping them inside vault.rdpv
means an attacker cannot reset the failure counter without touching the very
file they are attacking.

V=1 vaults load unchanged (missing Recovery / Policy / Fails default in) and are
rewritten as V=2 on the next save.

Payload (decrypted Data): { "Profiles": [...], "Settings": {...} }
RdpProfile: Id, Name, Host, Port, Username, Password, UseMultiMon, GatewayHost,
  FullScreen, Width, Height, AllowClipboard, AllowDrives, AllowPrinters,
  AllowSmartCards, AllowUnverifiedServer, CertThumbprint, Notes.
  Overrides (TriStateOverride: InheritGlobal, Enabled, Disabled):
    - SuppressCertWarningsOverride
    - FullScreenOverride
    - MultiMonOverride
    - AllowClipboardOverride
  Wake-on-LAN (WOL):
    - EnableWol (bool)
    - WolMacAddress (string, strictly validated & auto-normalized to XX:XX:XX:XX:XX:XX)
    - WolBroadcastIp (string, default "255.255.255.255")
    - WolPort (int, default 9)
    - WolWaitSeconds (int, delay 0-300s before RDP connection starts)
VaultSettings:
  - LockMinutes (60)
  - KillSessionsOnUsbRemoval (true)
  - SuppressCertWarnings (false, global default: strict server identity verification with vault cert pinning; opt-in per profile or global)
  - DefaultFullScreen (true, global default: launch sessions in full screen)
  - DefaultUseMultiMon (true, global default: span all monitors)
  - DefaultAllowClipboard (true, global default: clipboard copy/paste shared across sessions)
  - ForceMultiMon (synced with DefaultUseMultiMon)
  - DeepSweep (false)
  - SweepScope (OwnHostsOnly)
  - WarnIfDriveNotEncrypted (true)

Error messages: Wrap tag failure -> "Wrong password." Data tag failure or JSON
failure -> one sentence pointing at the .bak file.

Atomic save: write vaultPath + ".tmp", copy the current vault to ".bak", then
File.Replace. There is always one previous good copy on disk.

IMPORTANT: a password change re-salts the KDF AND wipes ALL seals (treated as a
possible compromise), so every PC must re-enroll Hello. Preserve this.

SECTION 5 — RUNTIME MECHANICS (END-TO-END FLOWS)
--------------------------------------------------------------------------------
5.1 STARTUP  (App.OnFrameworkInitializationCompleted — the ONE place that decides)
    --uninstall present                          -> UninstallWindow
    running from %LOCALAPPDATA%\RDPVault
      OR a vault.rdpv sits next to the exe       -> MainWindow
    otherwise                                    -> SetupWindow

5.2 FIRST RUN
    MainWindow shows a "no vault found" panel with a single "Create a new vault"
    button. That opens Dialogs.CreateVaultAsync (password + confirmation +
    10-character minimum + strength read-out), creates the vault, then forces the
    Recovery Code screen, which cannot be dismissed until acknowledged.
    Typing into the unlock box NEVER creates a vault.

5.3 UNLOCK (password)
    MainWindow.SubmitPasswordAsync -> Task.Run(SessionManager.UnlockWithPassword)
    -> cooldown check -> VaultCrypto.Open -> ClearFailures -> AfterUnlock().
    On failure: SecurityEnforcer.RecordFailure (see 5.9).

5.4 UNLOCK (Recovery Code)
    "I forgot my master password" -> Dialogs.AskRecoveryCodeAsync ->
    SessionManager.UnlockWithRecoveryCode -> VaultCrypto.OpenWithRecoveryCode.

    R1: on success SessionManager.UnlockedViaRecovery is set, and MainWindow runs
    OfferPasswordResetAfterRecoveryAsync immediately: change-password dialog with the
    CURRENT-password field hidden, then an offer to regenerate the Recovery Code.
    ChangePassword(null, new) skips proof-of-knowledge while that flag is set — the
    master key is already unwrapped by a 256-bit secret, so there is nothing left to
    prove. Declining leaves a persistent warning strip explaining how to finish later.
    The flag is cleared on a successful change, on lock, on dispose, and by any
    password or Hello unlock.

    NEVER go back to demanding the old password here. That was the bug: the app told
    the user to change a password it then refused to change without the one thing they
    had just proved they did not have.

5.5 UNLOCK (Windows Hello)
    Attempted automatically 300 ms after the window loads when a seal exists for
    this MachineId, and on demand from the button.

    FOREGROUND HANDLING (issue #21). KeyCredentialManager has no interop for
    passing an owner HWND — unlike UserConsentVerifier — so its prompt is hosted
    unparented by CredentialUIBroker.exe / LogonUI.exe and routinely opened
    behind the app without focus. A fingerprint presented to the sensor at that
    point is discarded, forcing the user to click the dialog first.
    Every KeyCredentialManager call is therefore wrapped in
    SystemPromptFocus.Begin(), which:
      1. activates our own window so this process holds the foreground;
      2. calls AllowSetForegroundWindow(ASFW_ANY) so the broker may take it;
      3. runs a 120 ms watchdog that locates the broker's visible top-level
         window (by class "Credential Dialog Xaml Host", or by owning process)
         and keeps it topmost and focused via AttachThreadInput +
         SetForegroundWindow until the scope is disposed, then releases topmost.
    The watchdog only ever touches windows owned by the known broker processes.
    Whichever window may raise the prompt must call SystemPromptFocus.SetOwner
    with its own HWND first — MainWindow does this on Loaded and before each
    attempt, SettingsWindow before enrollment, and MainWindow takes ownership
    back when the Settings dialog closes.

5.6 CONNECT & SESSION VALIDATION
    MainWindow.ValidateAndLaunchProfileAsync(profile, fromShortcut) -> RdpLauncher.LaunchAsync(profile):
     1. Touch() the idle timer.
     2. Session Validation: RdpLauncher.FindActiveSession(profile) checks if an mstsc
        process is already active for this host:port. If found, a warning dialog prompts
        the user: "Disconnect & Connect" (terminates old session cleanly and proceeds)
        or abort (preserves active session).
     3. Wake-on-LAN (WOL): If EnableWol is checked and WolMacAddress is provided,
        RdpLauncher.SendWakeOnLanAsync broadcasts a magic packet to WolBroadcastIp:WolPort,
        then awaits WolWaitSeconds (0-300s delay) allowing the remote machine to wake.
     4. Build .rdp: writes %TEMP%\rdpv_{Id}.rdp resolving clipboard, display, and cert warnings
        from profile overrides or global VaultSettings.
     5. If a password is saved: SessionCredentialCoordinator acquires reference-counted
        GENERIC credentials with CRED_PERSIST_SESSION for BOTH "TERMSRV/{Host}" and, when
        the port is not 3389, "TERMSRV/{Host}:{Port}". The password never enters the .rdp file.
     6. Process.Start(System32\mstsc.exe, "<temprdp>").
     7. A background task monitors exit asynchronously without blocking thread-pool threads.
        On exit: captures accepted cert thumbprint (if any), deletes temp .rdp, releases
        reference-counted credentials, sweeps traces, and raises SessionEnded.
     8. LiveSessions tracks active sessions for LiveCount(), KillAll(), and exit prompts.
     9. When launched via shortcut (fromShortcut == true), MainWindow minimizes to the taskbar
        upon launch, ensuring mstsc holds foreground focus without vault distraction.

5.7 AUTO-RELOCK
    A 1 s DispatcherTimer (created and started ON THE UI THREAD) locks the vault
    once LockMinutes of inactivity have passed. Activity = unlock, connect,
    shortcut creation, opening or saving Settings and the profile editor, any
    pointer or key event inside the window, and pipe messages. Locking never
    closes running RDP windows. The header shows a live "locks in mm:ss".

5.8 LOCK / EXIT
    Lock(): zero masterKey, drop payload, raise Locked, optional KillAll, then
    DeepSweep() if the setting is on else Sweep(), then TraceCleaner.ForgetHosts()
    so host names are not retained in memory. Dispose() does the same.
    Closing the window while RDP sessions are open asks for confirmation first.

5.9 BRUTE-FORCE HANDLING
    Always on: after 5 failures inside the window, each further attempt is
    refused until an escalating delay (2, 4, 8 ... 60 s) has elapsed.
    Optional: self-destruct. OFF by default; cannot be armed until a Recovery
    Code exists; requires typing ERASE; attempts clamped to 5-500. When it fires,
    vault.rdpv, its .bak and its .tmp are overwritten with random bytes and
    deleted, and the UI says exactly what happened.

5.10 SINGLE INSTANCE + SHORTCUTS & FOREGROUND SUPPRESSION
    Mutex Local\RDPVault_SingleInstance. A second instance sends "SHOW" or
    "LAUNCH:<profileId>" over pipe RDPVault_Show and exits immediately.
    Desktop shortcuts are real .lnk files targeting RDPVault.exe --launch <profileId>.
    The installer also registers .rdpvlink -> RDPVault.Link for legacy compatibility.
    When a shortcut is clicked:
      - If unlocked: directly validates and launches the profile, then minimizes MainWindow.
      - If locked: brings vault to foreground for password/Hello unlock, launches upon unlock,
        then minimizes MainWindow to taskbar so mstsc takes the foreground.
      - Auto-lock timer and trace cleaner continue running normally in the background.

5.11 USB REMOVAL
    2 s poll of AppContext.BaseDirectory / Environment.ProcessPath.
    R3: the drive must be missing for 3 CONSECUTIVE polls (UsbMissesBeforeShutdown,
    ~6 s) before anything happens, and one successful poll resets the counter. A single
    transient miss — AV lock, sleep/resume, slow controller, network hiccup — used to
    kill every open remote desktop. On confirmed loss: raise UsbRemoved, then Lock
    (killing sessions per setting), DeepSweep and Environment.Exit(0) all run OFF the
    UI thread after a 2.5 s grace period, so the on-screen explanation actually renders
    before the process ends.

5.12 UNINSTALL
    UninstallWindow asks first: "keep my vault" (default — copies vault.rdpv and
    its .bak to Documents\RDP Vault Backups before anything is removed) or
    "erase my vault" (requires typing ERASE; overwrite-then-delete).
    --quiet always takes the KEEP path: a silent uninstall must never destroy
    user data.

--------------------------------------------------------------------------------
SECTION 6 — TRACE CLEANING SPEC
--------------------------------------------------------------------------------
All in TraceCleaner.cs. Every step is TryRun-wrapped; cleanup must never crash
or block. Sweep() runs after each RDP window closes, on unlock, on lock and on
exit. DeepSweep() = Sweep() + credential wipe.

SweepScope.OwnHostsOnly (DEFAULT):
 1. HKCU\...\Terminal Server Client — delete MRU values whose DATA matches a
    vault host; inside "Default", delete values matching a vault host; inside
    "Servers", delete only subkeys matching a vault host.
 2. Documents\Default.rdp — deleted only if it references a vault host.
 3. Jump lists — *.automaticDestinations-ms deleted only if they contain both
    "mstsc" and a vault host.
 4. Recent items — only rdpv_* and names mentioning a vault host.
 5. %TEMP%\rdpv_*.rdp — always.
 6. UserAssist and Prefetch — NOT touched (they prove only that mstsc ran and
    are shared with the user's non-vault usage).
 7. DeepSweep credential wipe — only TERMSRV/* targets naming a vault host.

SweepScope.Everything (opt-in, spelled out in Settings): the v1.0.0 behaviour —
every MRU value, the whole Servers and Default subtrees, every mstsc jump list,
every *.rdp* in Recent, UserAssist ROT13 mstsc counters, MSTSC.EXE-*.pf, and
every TERMSRV/* credential.

DELIBERATELY NOT touched in either mode: Windows Event Logs, RDP server-side
logs, anything outside the current user's profile. Say so honestly in README.

SECTION 7 — GENERATED .RDP FILE (RdpLauncher.BuildRdpFile)
--------------------------------------------------------------------------------
UTF-8 (no BOM) at %TEMP%\rdpv_{Id}.rdp. Notable settings:
  screen mode id / desktopwidth / desktopheight / use multimon <- resolved from
    profile settings and global VaultSettings (DefaultFullScreen, DefaultUseMultiMon)
  full address:s:<host> or <host>:<port> when port != 3389
  redirectclipboard:i:<0|1> <- resolved from profile AllowClipboard / AllowClipboardOverride
    and global VaultSettings.DefaultAllowClipboard (default: 1 enabled)
  redirectprinters / redirectsmartcards <- profile toggles
  redirectdrives + drivestoredirect:s:* ONLY when AllowDrives is true
  username:s:<username> (password NEVER here)
  gatewayhostname / gatewayusagemethod / gatewayprofileusagemethod
  authentication level:i:<0|2> <- resolved from profile SuppressCertWarningsOverride
    and global VaultSettings.SuppressCertWarnings (default: 2 warn & verify with cert pinning)
  enablecredsspsupport:i:1 - negotiate security layer:i:1
  prompt for credentials:i:0 - autoreconnection enabled:i:1 - pcb:s:

  THE ACTUAL mstsc VALUES:
    0 = connect and DO NOT warn (selected when warning suppression is checked)
    1 = do NOT connect if the server cannot be verified
    2 = warn, and let the user connect or refuse (default in VaultSettings.SuppressCertWarnings;
        accepted cert thumbprints are pinned into vault.rdpv and restored before launch)

  Wake-on-LAN (WOL) Support & Live Progress:
    When enabled on a profile, RdpLauncher.SendWakeOnLanAsync constructs the 102-byte UDP
    magic packet (6x 0xFF followed by 16 repetitions of the 6-byte target MAC) and dispatches it
    concurrently across:
      (a) bound sockets on every active local network interface (forcing packets onto each physical NIC,
          bypassing Windows multi-NIC routing stalls and virtual adapter black holes),
      (b) subnet-directed broadcasts calculated dynamically per interface (e.g. 192.168.1.255),
      (c) the target Host IP or hostname (resolved via DNS for WAN/VPN/unicast WOL),
      (d) global broadcast (255.255.255.255) and any custom broadcast IP,
      (e) ports: configured WolPort (default: 9), alternative echo port (7), and the profile's
          custom RDP port (e.g. 11), ensuring packets penetrate router port forwarding rules.
    If WolWaitSeconds > 0, the launcher executes a deterministic 1-second interval countdown
    emitting LaunchProgressUpdate events with detailed target/port telemetry to the UI's tactical
    overlay modal with an active Cancel button before invoking mstsc.exe.

  Active Session Validator:
    RdpLauncher.FindActiveSession checks live mstsc processes against the target host:port.
    If an existing session is detected, a confirmation dialog lets the user terminate the older
    session or abort, preventing conflicting connections.

Defaults: deny-by-default for drives, printers, smart cards, and cert warning suppression;
allow-by-default for clipboard, full screen, and multi-monitor.

Session credential: CredWriteW Type=GENERIC, TargetName "TERMSRV/{Host}" and
"TERMSRV/{Host}:{Port}" when non-default, blob = UTF-16LE password,
Persist = CRED_PERSIST_SESSION, reference-counted in SessionCredentialCoordinator,
deleted when the mstsc window exits.

SECTION 9 — SECURITY MODEL SUMMARY
--------------------------------------------------------------------------------
Protects against:
  - Forensic discovery of RDP targets on the host PC after use (per SECTION 6,
    within the chosen scope).
  - Theft of the drive: AES-256-GCM + Argon2id(64 MiB). BitLocker is recommended
    and its status is reported honestly.
  - Offline brute force of the file: memory-hard KDF.
  - In-app brute force: escalating delay, counter stored inside the vault file.
  - Credential leakage at rest: RDP passwords never touch the .rdp file; session
    credentials are Persist=SESSION and deleted on window close.
  - Server impersonation: authentication level 2 by default.
  - In-person credential theft (shoulder-surfing) & screen scraping: Master
    password input controls strictly omit plaintext unmasking/revealing capabilities.
    Passwords flow exclusively inward into Argon2id key derivation, never outward
    to display buffers.

Assumes / does NOT protect against (be honest in any fork):
  - An attacker with the user's unlocked Windows session on a Hello-enrolled PC.
  - Memory forensics on a running unlocked instance. .NET strings holding
    profile passwords cannot be reliably zeroed; only the master key is.
  - Windows Event Log / EDR telemetry of mstsc execution.
  - Deleted-file carving. The vault shredder is best effort; SSD wear levelling
    and copy-on-write filesystems can defeat overwrite-in-place.
  - Anyone who copies vault.rdpv before attacking it — the in-vault failure
    counter and self-destruct only govern this app's own attempts.

The 20 findings closed in 1.1.0, in the order they were ranked:

    confirmation. Replaced by Dialogs.CreateVaultAsync.

    limit was ignored (null Payload) and 0/1 were accepted. Reworked: counter

SECTION 17 — COMPREHENSIVE ARCHITECTURAL, SECURITY & UX AUDIT RESOLUTION (SEPTEMBER 2026)
--------------------------------------------------------------------------------
Resolutions for the 10 system-level audit findings and the tactical UX overlay:

 1. PORTABLE LAUNCH UAC ELEVATION & INSTANCE TERMINATION BUG (Issue 1):
    In Program.cs, `isSetupOrMaintenance` previously checked `!InstallerService.IsInstalledLocation() && !File.Exists(AppPaths.VaultPath)`.
    This erroneously treated any first-time run from a portable drive without an existing vault
    as an administrative installer invocation, prompting for UAC elevation and terminating
    any running instances. The condition was removed. Portable runs launch cleanly as standard
    user processes and open the initial setup/create vault wizard directly.

 2. TACTICAL PROGRESS OVERLAY & LIVE COUNTDOWN FEEDBACK (Issue 2 & UX Mandate):
    Eliminated blank/unresponsive UI states during connection and unlock.
    - OverlayLaunch modal in MainWindow.axaml features an active indeterminate/determinate
      ProgressBar, tactical status text (TxtLaunchStep), a live remaining-seconds countdown
      (TxtLaunchCountdown), and an immediate Cancel button (BtnCancelLaunch).
    - RdpLauncher emits granular LaunchProgressUpdate events with CancellationToken support:
      "Validating active sessions", "Sending Wake-on-LAN magic packet...",
      "Waiting for host to wake up...", "Pinning server certificate...", "Injecting session credentials...",
      and "Starting Remote Desktop (mstsc)...".
    - WOL wait executes a deterministic 1-second countdown loop rather than an unresponsive delay,
      allowing the user to abort at any moment.
    - LockedPanel features an unlock ProgressBar (ProgUnlock) with KDF Argon2id derivation
      telemetry ("Deriving encryption keys with Argon2id (64 MiB)...", "Verifying hardware seal...").

 3. SELF-SABOTAGING RUNTIME ASSEMBLY DELETION (Issue 3):
    TraceCleaner previously purged `%TEMP%\.net\*` via CleanBundleResidue() inside routine
    trace cleaning sweeps. In single-file self-contained mode, .NET extracts native dependencies
    (`libSkiaSharp.dll`) into `%TEMP%\.net\RDPVault\<hash>`. Sweeping this folder while running
    either deleted active dependencies or locked them, corrupting subsequent UI rendering.
    Removed CleanBundleResidue from routine Sweep() and SweepHosts(), reserving bundle cleaning
    strictly for uninstallation.

 4. RESOLUTION PRESET VS. FULLSCREEN INHERITANCE CONFLICT (Issue 4):
    In ProfileEditorWindow, selecting an explicit windowed resolution (e.g. 1920x1080)
    previously left FullScreenOverride set to "Inherit Global". If global DefaultFullScreen
    was enabled (the default), mstsc ignored the explicit dimensions and launched fullscreen.
    Implemented bidirectional synchronization: selecting any windowed resolution automatically
    switches FullScreenOverride to "Disabled", and RdpProfile.ResolveFullScreen now explicitly
    honors windowed width/height parameters.

 5. EPHEMERAL AES-256-GCM IN-MEMORY CREDENTIAL PROTECTION (Issue 5):
    Implemented `VaultMemoryGuard` in Models.cs. Instead of retaining cleartext passwords
    in managed string memory throughout the entire session lifecycle where memory dumps
    could expose them, RdpProfile stores passwords as protected byte payloads encrypted with
    a session-scoped ephemeral 256-bit AES-GCM key. Plaintext byte arrays are pinned and
    cryptographically wiped (`CryptographicOperations.ZeroMemory`) immediately after consumption.

 6. CONCURRENT VAULT SAVES & ATOMIC REPLACEMENT DEADLOCK PROTECTION (Issue 6):
    VaultCrypto.Save previously used bare File.Replace without locking or retry backoff.
    Rapid sequential saves (profile edits, settings changes, cert pinning updates) or transient
    anti-virus locks could cause IOException file collisions and corrupt save operations.
    Implemented a thread synchronization lock (`SaveLock`) combined with an exponential backoff
    retry loop (5 attempts with jittered delays) and verified backup swapping (`vault.rdpv.tmp`
    replaced into `vault.rdpv` with `vault.rdpv.bak`).

 7. NAMED PIPE SERVER MULTI-CLIENT CONCURRENCY (Issue 7):
    SessionManager.PipeLoop previously ran a single sequential pipe server loop. When an external
    process or duplicate launch connected, the pipe server was blocked until completion, dropping
    or timing out concurrent launch requests. Upgraded to multi-client asynchronous connection
    handling using `NamedPipeServerStream.MaxAllowedServerInstances` with immediate loop recycling.

 8. TRACE CLEANER RESIDUE AUDIT & TELEMETRY (Issue 8):
    TraceCleaner previously swallowed all file deletion failures silently with empty catch blocks,
    leaving the user unaware if locked temporary .rdp files or session artifacts remained on disk.
    Implemented `SweepReport` struct and detailed telemetry reporting. TraceCleaner records total
    files inspected, items cleaned, and any locked files encountered, returning a tactical
    readout displayed directly on MainWindow's status strip.

 9. SERVER IDENTITY WARNING SUPPRESSION BY DESIGN & VAULT CERT PINNING:
    By deliberate design and explicit desire of the author, `SuppressCertWarnings` defaults
    to `true` (authentication level: 0) across both Windows and Android to guarantee zero
    warning fatigue and seamless one-click connectivity across private LANs, self-signed certificates,
    and direct IP connections. For users requiring strict verification, `SuppressCertWarnings` can
    be toggled in General Settings or overridden per-profile via TriStateOverride. When enabled, accepted
    server certificate thumbprints are pinned into `vault.rdpv` and pre-seeded into the Windows
    Terminal Server Client registry before launch.

 10. REAL-TIME SEARCH & FILTERING (Issue 10):
     Added real-time search filtering in MainWindow (`TxtSearch`). Profile cards are filtered
     instantly across profile Name, Host, Username, and Notes with a quick clear button,
     enabling rapid discovery and keyboard-driven navigation across large inventories.

================================================================================
19.A — PRODUCT DECISIONS THAT LOOK LIKE BUGS AND ARE NOT
================================================================================

 19.A.1  STORED REMOTE PASSWORDS ARE NOT VIEWABLE OUTSIDE THE PROFILE EDITOR.
         *** THIS IS INTENTIONAL. DO NOT "FIX" IT. ***

         Policy, in full:
           - A remote desktop password can be TYPED and CHANGED while editing the
             connection it belongs to, and REVEALED there with the eye toggle
             (BtnToggleProfilePass in Views/MainView.axaml).
           - Nowhere else in the app may a stored password be shown, copied,
             exported, logged, or placed on the clipboard. Not on connection
             cards, not in the launch overlay, not in Settings, not in a
             notification, not in logcat.
           - There is no "copy password" affordance anywhere, at all.
           - The only automated path out of the vault is RdpAutoTypeService,
             which holds the credential in volatile memory for at most 45 seconds
             and wipes it the instant it is injected.

         Rationale (owner's decision, 2026-09-21): once a password is set there is
         no routine reason to look at it. Every viewing surface is another place a
         credential can leak — a shoulder, a screenshot, a screen recorder, a
         clipboard monitor, a keyboard history cache. Confining the reveal to
         explicit edit mode keeps exactly one place where the secret can surface,
         and that place already requires an unlocked vault plus a deliberate
         navigation into that specific profile.

         Consequence that is accepted, not overlooked: if Auto-Type cannot find
         Microsoft Remote Desktop's password field, the user must open
         Edit on that connection, read the password there, and type it. The app
         now says exactly that, in the launch overlay and in the Auto-Type failure
         notification, instead of leaving the user stranded.

         REGRESSION GUARD: any future change that adds a password reveal, copy,
         share, export or log outside the profile editor is a regression against
         this section.

 19.A.2  "END SESSION" CANNOT DISCONNECT MICROSOFT REMOTE DESKTOP.
         Android sandboxing forbids one app terminating another app's session.
         The UI must never claim otherwise. See 19.B.2.

19.C — ARCHITECTURAL FINDINGS RESOLVED

 19.C.1  *** CRITICAL: BIOMETRICS WERE DECORATIVE. NOW THEY ARE BINDING. ***
         Before (shipped in 1.1.0): AndroidHardwareKeyStore.GenerateHardwareKey()
         accepted a `requireBiometrics` parameter AND IGNORED IT. It never called
         SetUserAuthenticationRequired(true). BiometricPrompt was shown, and then
         a Cipher was obtained and used SEPARATELY — the two events were
         unrelated. The master key could be unsealed from the Keystore with no
         biometric at all. Every "StrongBox / TrustZone / Class 3 gate" claim in
         SECTION 18.2 was false in code.

         After:
           - GenerateHardwareKey sets SetUserAuthenticationRequired(true),
             SetUserAuthenticationValidityDurationSeconds(-1) ("authorise every
             single use, strong biometric only"; API 30+ maps this onto
             AUTH_BIOMETRIC_STRONG), SetInvalidatedByBiometricEnrollment(true) and
             SetRandomizedEncryptionRequired(true).
           - EVERY seal/unseal goes through BiometricPrompt.CryptoObject.
             AuthenticateWithCryptoAsync() returns the Cipher the Keymaster
             authorised, and that exact Cipher performs the DoFinal.
             EnrollAndSealAsync() and AuthenticateAndUnsealAsync() are the only
             supported entry points.
           - A failed enrolment deletes the orphan key alias.

         CONSEQUENCE, BY DESIGN: enrolling a new fingerprint or face, or removing
         the screen lock, now DESTROYS the seal instead of silently extending
         vault access to the new finger. The app detects this
         (IsKeyInvalidated / HasKey) and says so in words.

         REGRESSION GUARD: calling BiometricPrompt without a CryptoObject, or
         generating a wrap key without SetUserAuthenticationRequired(true), is a
         regression against this section.

 19.C.2  THE SESSION BANNER NO LONGER GUESSES.
         RdpSessionService now TCP-probes the target every 20s (2.5s timeout, two
         consecutive failures) and reports "not responding" in both the ongoing
         notification and the in-app banner (which turns red). It still never
         claims to know that the RDP session itself is alive — RDP Vault does not
         own that socket. All strings are phrased "handed off" / "responding" /
         "not responding". The service also gained ActionStartSession, so a
         cold-start Connect that outruns the bind still posts its foreground
         notification within Android's 5-second window, and a proper monochrome
         status icon (Resources/drawable/ic_stat_vault.xml) instead of
         android.R.drawable.ic_menu_share.

 19.C.3  SEAL REPAIR IS CONSENTED, NOT SILENT.
         Before: after a password unlock the app silently called
         GenerateHardwareKey(newKeyId) with no requireBiometrics argument and
         re-sealed. With 19.C.1 in force a re-seal now requires a real biometric

20.A — CERTIFICATE AND IDENTITY WARNING SUPPRESSION BY DESIGN
  Architectural Mandate: By deliberate design and explicit desire of the author,
  all SSL/TLS certificate, untrusted server, and identity warnings are suppressed
  by default across both the Windows desktop and Android mobile implementations:
  - Default Setting: `SuppressCertWarnings = true`.
  - Windows: Emits `authentication level:i:0` into the temporary `.rdp` file.
  - Android: Encodes `authentication%20level=i:0` into the launch `rdp://` URI.
  - Rationale: Eliminates warning fatigue on private subnets, home labs, dynamic
    IPs, and self-signed certificates. Full per-profile overrides remain available
    via `TriStateOverride` for enterprise environments requiring strict validation.

20.B — ISSUE 30: DESTINATION PORT PRESERVATION & ENFORCEMENT
  Defect: In certain Windows connection pathways, mstsc or Credential Manager fell
  back to default port 3389, ignoring the custom port in the profile card.
  Resolution:
  - Windows: `RdpLauncher.BuildRdpFile` outputs both `full address:s:{host}:{port}`
    and `server port:i:{port}`. `RdpLauncher.CredentialTargets` registers credentials
    under `TERMSRV/{host}`, `TERMSRV/{host}:{port}`, and `TERMSRV/{fullAddress}`.
  - Android: `ConnectionEndpoint.FromProfile` extracts and validates the port,
    adding `server%20port=i:{port}` to the URI query and formatting endpoint targets.
  - Suggestion: Default suggested port is 3389, but any custom port is strictly
    respected upon connection across all launch and credential coordination routines.

20.C — ISSUE 31: CROSS-PLATFORM PORT KNOCKING (ICMP KNOCK PROTOCOL)
  Feature: Pre-connection port knocking to open firewalls before initiating RDP.
  - Architecture: `IcmpKnock.cs` (in Core and linked to both desktop and Android).
  - UI: Collapsible card in profile editors (`Enable Port Knocking` checkbox toggles
    `PnlKnockDetails` / `PnlIcmpKnockDetails`). Includes signature generator button.
  - Magic Packet: Transmits out-of-the-ordinary ICMP payload sizes (configurable
    97 to 224 bytes, strictly rejecting default 32/64-byte echo requests) with
    embedded hex signature tokens.
  - Delay: Enforces an asynchronous 2000 ms delay following the knock transmission
    before initiating RDP launch or socket pre-flight probes, providing remote
    firewall daemons (e.g. knockd, iptables) adequate time to open the RDP port.

20.D — ISSUE 32: ANDROID ACCESSIBLE BOTTOM SAVE / BACK CONTROLS
  Defect: When scrolling down long profile forms on mobile screens, the header Save

SECTION 22 — TCP/HTTP PORT KNOCKING & CELLULAR REACHABILITY ENGINE (2026-09-25)
--------------------------------------------------------------------------------
22.A - ROOT CAUSES IDENTIFIED:
  1. `TcpClient()` IPv4-Only Socket Lock:
     - On modern cellular connections (single-stack IPv6 with 464XLAT/CLAT), `new TcpClient()` binds strictly to `AddressFamily.InterNetwork`.
     - Connecting to IPv4 targets (e.g. `94.159.233.218`) threw `ENETUNREACH` before any packet reached the cellular radio interface.
  2. Synchronous Handshake Requirement Aborting HTTP Knock:
     - Knock ports on stateful firewalls (RouterOS Mikrotik, iptables/nftables `recent` module) typically drop or consume knock packets silently without returning a TCP SYN-ACK.
     - Previous code waited for TCP handshake completion before attempting to send the HTTP payload. When the connection timed out, the socket was marked disconnected and the entire knock aborted without transmitting any HTTP data.
  3. Pre-flight Reachability False Negative & Cellular Misdirection:
     - `HostProbe.IsReachableAsync` also suffered from the `TcpClient` IPv4 socket lock, causing valid connections over mobile data to fail immediately.
     - Single-shot 1500ms probe failed to give stateful firewalls time to insert the client IP into their dynamic whitelist address lists.
     - The pre-flight failure dialog falsely blamed home/office Wi-Fi when connecting to public WAN IPs over cellular.

22.B - ARCHITECTURAL RESOLUTION:
  1. Dual-Path Concurrent Knock Engine (`IcmpKnock.cs`):
     - `SendHttpKnockAsync`: Dispatches an HTTP GET request with headers matching `curl -m 1 http://<host>:<port>` (`User-Agent: curl/8.0`, `Accept: */*`, `Connection: close`). Leverages Android OS platform HTTP stack which natively supports cellular APN routing and DNS64/NAT64.
     - `SendSocketSynKnockAsync`: Concurrently resolves dual-stack IP candidates (IPv4 direct and DNS64/NAT64 synthesized addresses) and initiates a raw TCP `Socket` connection with `NoDelay = true`. This guarantees TCP SYN transmission to trigger packet-filter knock rules regardless of whether the remote port sends a response.
  2. Dual-Stack Reachability & Preflight Retries (`HostProbe.cs` & `MainView.axaml.cs`):
     - `HostProbe.IsReachableAsync`: Uses non-blocking dual-stack candidate resolution (`System.Net.Sockets.SocketType.Stream`) with socket fallback.
     - `HostProbe.IsPrivateOrLocalHost`: Distinguishes private RFC1918 / mDNS / local LAN addresses from public WAN destinations.
     - `MainView.axaml.cs` (`RunPreflightAsync`): When `profile.EnableIcmpKnock` is true, probes up to 3 times (1.5s timeout, 1s delay between attempts) to provide sufficient window for stateful firewall address lists to activate before presenting the unreachable dialog. WAN destinations receive an accurate failure description rather than a generic local Wi-Fi advisory.

SECTION 23 — WAN WOL PIPELINE, STEALTH KNOCK (MIKROTIK DROP), AUTO-TYPE & BIOMETRIC REPAIR

23.A - WAKE-ON-LAN & STEALTH PORT KNOCKING PIPELINE:

     - Previously, Wake-on-LAN ran before port knocking. On firewalled routers (e.g. MikroTik RouterOS WAN drop rule), the router dropped the magic packet because the client source IP had not yet knocked to open `Roaming_Authorized`.
     - In both Windows (`RDPVault\RdpLauncher.cs`) and Android (`RDPVault.Android\Views\MainView.axaml.cs`), Port Knocking now executes FIRST. The router dynamically whitelists the source IP, allowing subsequent UDP WOL magic packets (port 9, 7, and RDP port) to traverse the firewall to the target host.
  2. WAN Unicast Wake-on-LAN:
     - On Windows and Android, `cleanHost` now strips embedded ports from `profile.Host` before DNS/IP resolution, ensuring magic packets correctly target the WAN host.
     - Android `RunWolSequenceAsync` no longer aborts on cellular connections (`HostProbe.IsWolCapableNetwork`). WAN WOL over mobile data is fully enabled.
  3. Non-Blocking Stealth Knock Engine (`RDPVault\IcmpKnock.cs`):
     - Concurrently issues non-blocking `Socket.ConnectAsync` and HTTP requests with a strict 800ms deadline.
     - Treats `OperationCanceledException` and `SocketException` as expected success, matching RouterOS `action=add-src-to-address-list` followed immediately by `action=drop`.

  2. Dialog Endpoint Matching:
     - In `MatchesEndpoint`, if Microsoft Remote Desktop's login dialog omits the custom port in its title (e.g. displaying `94.159.233.218` rather than `94.159.233.218:11`), the host match is authoritative, eliminating false negative verification failures.
  3. Action Button Traversal:

SECTION 25 — DUAL-MONITOR HOST PROTECTION & PORTRAIT RDP COLLAPSE PREVENTION
--------------------------------------------------------------------------------
25.A - ROOT CAUSE ANALYSIS (DESKTOP TOPOLOGY SCRAMBLE):
  1. Client-Side Limitation:
     - Microsoft Remote Desktop for Android (com.microsoft.rdc.androidx / Windows App) strictly ignores desktopwidth and desktopheight when dispatched via rdp:// URI schemes (verified against official Microsoft Learn RDP URI specifications).
     - If the phone is held vertically in portrait when launching, the client opens the session in portrait (e.g., 1080x1920 or 1220x2712) and requests that geometry from the Windows host.
  2. Host-Side Destructive Session Reconfiguration:
     - When Windows 11 Remote Desktop Services (TermService) attaches to a session with a portrait viewport:
       a) Windows shuts down the secondary physical 1920x1080 monitor.
       b) Windows resizes the primary desktop to 1080x1920 portrait.
       c) Windows forces all open applications across both monitors into the 1080-wide strip, clamping application windows.
       d) Windows Explorer rearranges all desktop icons to fit within the narrow vertical column.
       e) Disconnecting does not automatically restore scrambled desktop icon layouts.

25.B - ARCHITECTURAL FIXES & SAFEGUARDS:
  1. Pre-Handoff Landscape Enforcement (RDPVault.Android\Views\MainView.axaml.cs & RdpLauncher.cs):
     - When initiating connection to any desktop profile (width >= height), LaunchAsync immediately transitions MainActivity.Instance.RequestedOrientation to ScreenOrientation.SensorLandscape.
     - This guarantees the Android Window Manager surface is rotated into Landscape before com.microsoft.rdc.androidx is started, forcing the external RDP client to query landscape display metrics (width > height) and connect in landscape mode.
     - On app resume or if connection is cancelled prior to handoff, orientation cleanly reverts to ScreenOrientation.Unspecified.
  2. Prohibition of Dynamic Resolution (RDPVault.Android\Rdp\RdpLauncher.cs):
     - RDP URI query builder strictly enforces dynamic%20resolution=i:0 across all desktop launches, preventing Microsoft Remote Desktop from dispatching dynamic display control PDUs (MS-RDPEDISP) that resize the server desktop when rotated.
  3. Windows Host Display Policy & Window Persistence:
     - Enabled Windows 11 "Remember window locations based on monitor connection" via HKCU:\Control Panel\Desktop\RestorePreviousStateRecalcBehavior = 0.
     - Configured Terminal Services maximum resolution ceiling via HKLM:\SOFTWARE\Policies\Microsoft\Windows NT\Terminal Services: MaxXResolution = 3840, MaxYResolution = 1080. Any incoming remote connection requesting a height greater than 1080 (such as a portrait 1080x1920 phone) is clamped to 1080, preventing tall portrait desktop collapsing.
  4. External Client Display Settings Recommendation:
     - Inside Windows App / Microsoft Remote Desktop: configure Settings -> Display -> Orientation: "Lock to landscape" and Display resolution: "1920 x 1080".
